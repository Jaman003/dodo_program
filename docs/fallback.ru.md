# Резервный источник: `fallback-url`

Если основной источник конфигурации временно недоступен, DoDo может обновить её по заранее сохранённому резервному адресу. Это работает с обычными HTTPS-ссылками, поддерживаемым JSON и полными Xray-профилями, списками URI и Base64. Функция **не ограничена crypt1-ссылками**.

Здесь описаны iOS 2.2.0 и Android APK 2.2.0 (2107). В опубликованной Mac-версии этого механизма пока нет; поддержку Windows также не предполагаем. См. [совместимость платформ](compatibility.ru.md).

Регистрация в DoDo, платный доступ и API провайдера не нужны. Remnawave и собственные панели используют один HTTP-контракт.

## Заголовки ответа

Передавайте настоящие HTTP-заголовки, а не поля JSON и не комментарии внутри конфигурации:

| Заголовок | Значение | Правило |
|---|---|---|
| `fallback-url` | Полный HTTPS-адрес резервного источника этого пользователя. | Путь, токен и query задаёт провайдер. Одного домена недостаточно. |
| `providerid` | Необязательный постоянный ID сервиса, например `demo-vpn`. | Если сохранён вместе с резервом, резерв должен вернуть точно такое же значение. |

DoDo запоминает резерв только из пригодного успешного ответа, действительно полученного от исходного HTTPS-origin. Редирект или страница ошибки другого host не становятся доверенным источником резерва. Сам резерв может находиться на другом корректном HTTPS-домене.

Имена заголовков нечувствительны к регистру. **Значение** `providerid` чувствительно к регистру: 1–128 ASCII-символов; первый — буква или цифра, далее буквы, цифры, `.`, `-`, `_` или `:`. Не используйте вместо ID административный API-токен.

`providerid` — не премиум-доступ, лицензия Happ, HWID, ID кабинета провайдера и не доказательство владения сервисом. Он отличается от `x-dodo-provider-id` для [привязки и функций кабинета](provider-console.ru.md). Совпадение fallback-ID не открывает сторис, уведомления и чужих пользователей.

## Пример основного и резервного ответа

Основной адрес — только нерабочий пример:

```text
https://primary.example.com/sub/demo-token?format=json
```

В теле — действующая конфигурация пользователя, в заголовках:

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
providerid: demo-vpn
fallback-url: https://backup.example.com/sub/demo-token?format=json
```

Точный резервный адрес должен отдавать конфигурацию того же пользователя. Если основной ответ передал `providerid`, резерв тоже возвращает его:

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
providerid: demo-vpn
```

Без `providerid` резерв также работает по сохранённому точному HTTPS-адресу. Если ожидаемый ID был сохранён, но резерв его не вернул или изменил, обновление отклоняется, а прежние серверы остаются.

DoDo **не переносит** путь и токен на произвольный домен, не ищет адрес по ID, не угадывает `/json` и не идёт по цепочке зеркал. Полный рабочий резервный адрес должен задать провайдер.

## Настройка Remnawave или собственной панели

1. Подготовьте резервный сервис, DNS и действующий HTTPS-сертификат. Одна DNS-запись не создаёт резервный endpoint.
2. Резерв должен выдавать конфигурацию этого пользователя, а не страницу сайта. Согласуйте авторизацию, срок, трафик и ограничения устройств.
3. В разделе заголовков ответа конфигурации добавьте `fallback-url` и при необходимости `providerid`. Название раздела зависит от версии: **Response Headers / Additional Response Headers**.
4. Примените заголовки к нужным форматам и User-Agent, включая полный JSON. Не заменяйте остальные правила форматов.

В версиях Remnawave с переменными конфигурации в заголовках шаблон может выглядеть так:

```http
providerid: demo-vpn
fallback-url: https://backup.example.com/sub/{{SHORT_UUID}}
```

Проверьте, что ваша версия подставляет `{{SHORT_UUID}}`. В настоящем HTTP-ответе должен быть полный персональный URL, не нераскрытый шаблон и не одна ссылка на всех пользователей. Собственный бэкенд может сформировать такой адрес напрямую.

Другой домен на том же сервере иногда помогает при блокировке имени, но не при недоступности самого сервера или IP. Для этого резерву нужна отдельно доступная инфраструктура.

## Когда приложение пробует резерв

| Ошибка основного источника | Поведение |
|---|---|
| Сетевой сбой, таймаут, HTTP 408 или 5xx | Сохранённый резерв может быть запрошен в пределах общего времени и числа попыток. |
| Ошибка TLS-сертификата | Проверка сертификата не отключается, обхода через резерв нет. |
| Отказ авторизации, лимит HWID, явно отключённый или истёкший доступ | Ограничения не обходятся. |
| HTTP 404, 410 или 429 | Не обходятся через резерв. |

Используется один резерв: без цепочек и бесконечных повторов. В описанной мобильной базе общий предел операции — 25 секунд. Запросы используют тот же сохранённый HWID; повтор не сбрасывает лимит устройств.

Успешная загрузка обновляет ту же карточку, сохраняя идентичность исходной ссылки и порядок. При ошибке загрузки или проверки остаются прежние серверы и настройки — неполный ответ их не заменяет.

## Сначала резерв нужно узнать

Основной источник должен хотя бы раз успешно добавиться или обновиться в поддерживающей версии. Если он недоступен уже при первом импорте, приложение не может прочитать заголовок из недоступного ответа. Одного `providerid` для поиска резерва недостаточно.

Для [crypt1 и AGE1](crypto.ru.md) действуют те же правила. При `response: "age1-required"` основной и резервный адреса должны отдавать корректный AGE1; резерв не может заменить его открытым текстом. Метаданные остаются вне зашифрованного тела.

## Проверка у провайдера

- Сначала выполните обычное обновление и проверьте точный `fallback-url` в ответе сервера.
- Убедитесь, что резерв обслуживает того же пользователя и возвращает тот же регистрозависимый `providerid`, если он задан.
- Создайте допустимый сбой только основного адреса: полное отключение интернета не проверяет резерв.
- Проверьте неверный/отсутствующий ID и непригодное тело резерва: рабочая конфигурация должна сохраниться.
- Проверьте настоящее VPN-подключение отдельно от успешного обновления конфигурации.
- Не публикуйте реальные токены в скриншотах, логах и обращениях.
