# منبع پشتیبان با `fallback-url`

اگر منبع اصلی پیکربندی موقتاً در دسترس نباشد، DoDo می‌تواند از نشانی پشتیبانی که قبلاً ذخیره شده، به‌روزرسانی کند. این قابلیت با HTTPS معمولی، JSON پشتیبانی‌شده و پروفایل کامل Xray، فهرست URI و Base64 کار می‌کند و **محدود به crypt1 نیست**.

این صفحه مربوط به iOS 2.2.0 و Android APK 2.2.0 (2107) است. نسخهٔ منتشرشدهٔ Mac این سازوکار را ندارد؛ پشتیبانی Windows نیز فرض نمی‌شود. [سازگاری پلتفرم‌ها](compatibility.fa.md) را ببینید.

ثبت‌نام DoDo، دسترسی پولی یا API ارائه‌دهنده لازم نیست. Remnawave و پنل اختصاصی از همین قرارداد HTTP استفاده می‌کنند.

## هدرهای پاسخ

این موارد باید هدر واقعی HTTP باشند، نه فیلد JSON یا توضیح داخل پیکربندی:

| هدر | مقدار | قانون |
|---|---|---|
| `fallback-url` | نشانی کامل HTTPS منبع پشتیبان همین کاربر. | مسیر، توکن و query را ارائه‌دهنده تعیین می‌کند؛ نام دامنه به‌تنهایی کافی نیست. |
| `providerid` | شناسهٔ اختیاری و ثابت سرویس، مانند `demo-vpn`. | اگر همراه پشتیبان ذخیره شد، پاسخ پشتیبان باید دقیقاً همان مقدار را برگرداند. |

DoDo تنها از پاسخ موفق و قابل‌استفاده‌ای که واقعاً از HTTPS origin اصلی آمده، پشتیبان را یاد می‌گیرد. redirect یا صفحهٔ خطای میزبان دیگر، منبع قابل‌اعتماد ثبت پشتیبان نیست. خود نشانی پشتیبان می‌تواند روی دامنهٔ معتبر HTTPS دیگری باشد.

نام هدر به بزرگی/کوچکی حروف حساس نیست. **مقدار** `providerid` حساس است و باید 1–128 نویسهٔ ASCII داشته باشد: ابتدا حرف یا عدد، سپس حرف، عدد، `.`، `-`، `_` یا `:`. از توکن مدیریتی API به‌عنوان ID استفاده نکنید.

`providerid` دسترسی پولی، مجوز Happ، HWID، شناسهٔ حساب پنل یا اثبات مالکیت نیست. این با `x-dodo-provider-id` برای [اتصال ارائه‌دهنده و قابلیت‌های پنل](provider-console.fa.md) فرق دارد. یکسان بودن ID پشتیبان، دسترسی استوری، اعلان یا کاربران ارائه‌دهندهٔ دیگر نمی‌دهد.

## نمونهٔ پاسخ اصلی و پشتیبان

نشانی زیر صرفاً مثال غیرعملیاتی است:

```text
https://primary.example.com/sub/demo-token?format=json
```

بدنه، پیکربندی معتبر کاربر را دارد و هدرها چنین‌اند:

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
providerid: demo-vpn
fallback-url: https://backup.example.com/sub/demo-token?format=json
```

همین نشانی دقیقِ پشتیبان باید پیکربندی همان کاربر را ارائه کند. اگر منبع اصلی `providerid` داد، پشتیبان نیز آن را برگرداند:

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
providerid: demo-vpn
```

بدون `providerid` نیز پشتیبان با نشانی دقیقِ ذخیره‌شده کار می‌کند. اگر ID مورد انتظار ذخیره شده ولی پشتیبان آن را حذف یا تغییر دهد، DoDo به‌روزرسانی را رد می‌کند و سرورهای قبلی می‌مانند.

DoDo مسیر/توکن را به دامنهٔ دلخواه **منتقل نمی‌کند**، با ID نشانی پیدا نمی‌کند، `/json` را حدس نمی‌زند و زنجیرهٔ mirror را دنبال نمی‌کند. ارائه‌دهنده باید نشانی کاملِ کارکرده را بدهد.

## تنظیم Remnawave یا پنل اختصاصی

1. سرویس پشتیبان، DNS و گواهی معتبر HTTPS را آماده کنید. یک رکورد DNS به‌تنهایی endpoint پشتیبان نمی‌سازد.
2. پشتیبان باید پیکربندی همان کاربر بدهد، نه صفحهٔ وب. احراز هویت، انقضا، سهم ترافیک و محدودیت دستگاه را هماهنگ نگه دارید.
3. `fallback-url` و در صورت نیاز `providerid` را در هدرهای پاسخ پیکربندی اضافه کنید. نام بخش بسته به نسخه فرق دارد: **Response Headers / Additional Response Headers**.
4. هدرها را برای قالب‌ها و قواعد User-Agent موردنظر، از جمله JSON کامل، فعال کنید؛ قواعد دیگر قالب پاسخ را جایگزین نکنید.

در نسخه‌های Remnawave که متغیر پیکربندی را در هدر پشتیبانی می‌کنند، الگو ممکن است چنین باشد:

```http
providerid: demo-vpn
fallback-url: https://backup.example.com/sub/{{SHORT_UUID}}
```

بررسی کنید نسخهٔ شما `{{SHORT_UUID}}` را جای‌گذاری می‌کند. پاسخ واقعی HTTP باید URL کامل یک کاربر را داشته باشد، نه الگوی بازنشده یا یک نشانی شخصی برای همه. بَک‌اند اختصاصی می‌تواند همین URL دقیق را مستقیماً بسازد.

دامنهٔ دیگر روی همان سرور ممکن است در مسدودسازی نام کمک کند، اما خرابی خود سرور یا IP را حل نمی‌کند. آن وضعیت، زیرساخت پشتیبانِ مستقل و قابل‌دسترسی می‌خواهد.

## چه زمانی پشتیبان امتحان می‌شود؟

| خطای منبع اصلی | رفتار |
|---|---|
| خطای شبکه، timeout، HTTP 408 یا 5xx | پشتیبان ذخیره‌شده ممکن است در سقف مشترک زمان/دفعات امتحان شود. |
| خطای گواهی TLS | اعتبارسنجی گواهی خاموش نمی‌شود و از پشتیبان برای دور زدن آن استفاده نمی‌شود. |
| رد احراز هویت، محدودیت HWID یا دسترسی صریحاً غیرفعال/منقضی | این محدودیت‌ها دور زده نمی‌شوند. |
| HTTP 404، 410 یا 429 | از طریق پشتیبان دور زده نمی‌شوند. |

فقط یک پشتیبان وجود دارد؛ نه زنجیره و نه تلاش بی‌پایان. زمان کل عملیات در نسخه‌های موبایلِ مستندشده 25 ثانیه است. درخواست‌ها همان HWID ذخیره‌شده را دارند؛ تلاش دوباره راه بازنشانی محدودیت دستگاه نیست.

در صورت موفقیت، همان کارت به‌روز می‌شود و هویت منبع اصلی و ترتیب کارت‌ها حفظ می‌شود. خطای بارگذاری یا اعتبارسنجی، سرورها و تنظیمات قبلی را نگه می‌دارد و نتیجهٔ ناقص جایگزینشان نمی‌شود.

## ابتدا باید پشتیبان ذخیره شده باشد

منبع اصلی باید حداقل یک بار در نسخهٔ پشتیبان این قابلیت، موفق افزوده یا تازه‌سازی شده باشد. اگر در اولین وارد کردن در دسترس نباشد، برنامه نمی‌تواند هدر پاسخِ دریافت‌نشده را بخواند. `providerid` به‌تنهایی نشانی پشتیبان را پیدا نمی‌کند.

همین قواعد برای [crypt1 و AGE1](crypto.fa.md) برقرار است. در `response: "age1-required"`، منبع اصلی و پشتیبان هر دو باید AGE1 معتبر بدهند؛ پشتیبان نمی‌تواند سیاست را به متن باز کاهش دهد. فراداده را بیرون بدنهٔ رمز‌شده نگه دارید.

## چک‌لیست آزمایش ارائه‌دهنده

- ابتدا تازه‌سازی عادی را انجام دهید و `fallback-url` دقیق را در پاسخ سرور بررسی کنید.
- تأیید کنید پشتیبان همان کاربر را سرویس می‌دهد و در صورت وجود، همان `providerid` حساس به حروف را برمی‌گرداند.
- خطای مجاز را فقط برای منبع اصلی شبیه‌سازی کنید؛ قطع کل اینترنت آزمایش پشتیبان نیست.
- ID غلط/حذف‌شده و بدنهٔ نامعتبر را امتحان کنید؛ پیکربندی کارکردهٔ قبلی باید بماند.
- اتصال واقعی VPN را جدا از موفقیت تازه‌سازی پیکربندی آزمایش کنید.
- توکن واقعی را در تصویر، لاگ یا پیام عمومی پشتیبانی قرار ندهید.
